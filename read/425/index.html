目录 scope 已经覆盖整棵子树，为什么 2.9.8 的五个 mission 还是要扩围：若其规划发生在 2.9.2 之后，目录探测已启用

目录形 scope 覆盖整棵子树，但探测仅在规划检出与 scope 放宽时发生，已有 mission 的 scope 不会被持续重探或自动重写，fileInScope 仍为纯 glob 匹配。release/2.9.8 合并波次中五个 mission 仍需扩围，规划日期原文未给出；越界要等 worker 完成、preflight 报错后才凭文件名重建 scope，issue 中的 footprint 与 scopeAdvice 仍是提案。

统计期间与来源日期：2.9.2 的变更记录标为 2026-11-18，该来源页未标注发布日期；issue 记录日期为 2026-11-21，对应 release/2.9.8 合并波次；本稿核查日为 2026-11-22。

研究问题与当前判断

目录 scope 已覆盖子树，为什么后续合并波次的任务还要事后扩围？

2.9.2 解决的是目录条目的匹配方式；2.9.8 的扩围记录中，部分遗漏文件符合计划阶段“文件存在、确实需要、无人列出”的信息缺口，且越界要到完成后才被发现。这一解释只覆盖部分文件，M166 的遗漏项含 host/doctor-links.js (new)，并非规划时已存在的文件，不能套用于全部五个 mission。五个 mission 的规划日期原文未给出，只有在规划发生在 2.9.2 之后时，才能把扩围与已启用的目录探测并列讨论。

匹配层修好了，时间层和知识层没修

2.9.2 把规划检出时探测到的目录存成覆盖子树的条目，这解决的是“写了目录却匹配不到其下文件”。但探测只在规划检出与 tower_mission 的 scope 放宽时发生，已存在 mission 的 scope 不会被持续重探或自动重写，fileInScope 仍是纯 glob 匹配[1]。这意味着规划后新增的目录不会自动触发对已存在 mission 的重新探测或重写 scope；若已通过 widen 把目录纳入 scope，围栏仍会随之变化。原文另描述 tower 在 preflight 之后执行 widen。第二层是知识：计划时校验能判断已列路径是否存在，却无法判断某个已存在、确实要改的文件为何没被列出[2]。两层都不在 2.9.2 的改动范围内，所以目录 scope 生效并不等于扩围消失。

越界在完成之后才被记录，补 scope 只剩文件名

issue 描述的顺序是 worker 先改 fence 外文件，完成后 preflight 报越界，再 widen；widen 在 worker 离开之后执行，只凭文件名重建 scope，CompleteInput 本身不含文件列表，diff 只能由 tower 侧事后算[2]。这使约束点落在后端：真正需要知道“要改哪些文件”的时刻在写入前，而可用信息出现在写入后。原文同时给了竞争解释——widen 因重叠被拒时要放弃并重规划，存在此类失败案例[2]——说明扩围路径本身也有代价，但原文未证明这些失败与计划遗漏互斥，不能简单归因于目录 scope 未覆盖。issue 提案中的 completion 时声明 footprint 与 outsideScope 返回 scopeAdvice 尚未实现，且同一提案保留 tower_preflight 的 out-of-scope blocker[2]。

最强反证与竞争解释

原文自身给出两处需要限定的地方：widen 因重叠被拒会导致放弃重规划，存在此类失败案例，但原文没有说明这些失败与计划遗漏互斥，不能据此把扩围原因归为补 scope 路径受限；issue 提案中的 outsideScope 非空仍可完成并返回 scopeAdvice 属于 Proposal，同一提案明确 tower_preflight 的 out-of-scope blocker 继续生效，因此不能据此推出当前门禁不是硬拦截[2]。若后续版本另设 scope 校验并前移到写入之前，则“顺序导致事后才发现”这一解释会被削弱[2]。

展开事实导语

2.9.2 的变更说明写明：tower_plan 的目录形 scope 现在覆盖整棵子树；改动前 scope 条目按纯文件 glob 匹配，规划 docs/guide 不会覆盖 docs/guide/quickstart.md，任务只能越出围栏去改门禁要求的文件。同一变更里，规划以及 tower_mission 的 scope 放宽会在规划检出里对每个裸条目探测一次，命中目录时存成目录形条目，带显式尾分隔符的条目即使目录尚不存在也按目录处理；glob、文件、未知路径与无法 stat 的条目保持原样。关键边界同时写在同一处：已存在 mission 上的 scope 永远不会被重写，fileInScope 仍是纯 glob 匹配器[1]。 到 release/2.9.8 合并波次，issue 记录五个已合并 mission 的计划 scope 与最终 scope 差距较大，并以表格逐 mission 列出计划 scope、最终 scope 和计划遗漏的文件或文件组[2]。该记录描述的当前顺序是：worker 先改 fence 外的文件，完成之后才由 preflight 报越界并 widen；widen 发生在 worker 离开之后，只凭文件名重建 scope，而 CompleteInput 不含文件列表，diff 只能事后从 tower 一侧计算；计划时的校验抓不到“文件存在、确实需要、无人列出”这种情形[2]。

一个具体限制

本稿只覆盖原文所述 2.9.2 的 scope 规则与 release/2.9.8 五个已合并 mission 的记录。原文未给出这五个 mission 的规划日期，无法确认其规划时 2.9.2 的目录探测是否已启用。给定变更日志只到 2.9.5，未提供 2.9.8 发布说明，也无运行日志与 scope 条目明细，因此无法确认具体触发点、越界文件相对目录条目或文件条目的位置，也无法判断越界是否全部由“存在且需要但未列出”造成；不外推到其他版本或全部任务。
